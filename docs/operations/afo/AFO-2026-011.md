# AFO-2026-011 — Gate PostgreSQL distribuído aborta por dependência rígida de worker indisponível

**Status:** ROOT_CAUSE_PROVEN  
**Classe:** CI control plane / disponibilidade / scheduling

### Descoberta

A falha foi encontrada durante a certificação OpenTelemetry do Generic Worker. As PRs #194 e #195 ficaram bloqueadas embora todos os checks GitHub-hosted relevantes estivessem verdes.

O check obrigatório `distributed-postgres` falhou antes de executar a suíte por não conseguir alcançar um dos workers configurados.

### Sintoma

O gate retorna falha com:

`ssh: connect to host 192.168.88.4 port 22: No route to host`

Esse endereço pertence ao host `note`, utilizado como `ProxyJump` para `ci03`.

### Evidência de runtime

Scheduler instalado e ativo no AGT:

`/usr/local/lib/andy-ci/bin/andy-ci-distributed`

Contrato observado:

- scheduler V1;
- pool rígido: `WORKERS=(ci03 ci01 ci02)`;
- preflight exige sucesso de todos os workers antes de prosseguir;
- descoberta inicial é fixada em `ci03`.

SSH efetivo:

- `ci03 -> ProxyJump note`;
- `note -> 192.168.88.4`.

Estado físico observado:

- `ci01`: SSH PASS, runner PASS, Docker PASS;
- `ci02`: SSH PASS, runner PASS, Docker PASS;
- `ci03`: indisponível porque `note` está inalcançável;
- ARP de `192.168.88.4`: `INCOMPLETE`.

Mesmo com 2/3 da capacidade disponível, o scheduler V1 falha o gate inteiro.

### Causa raiz

O scheduler V1 modela o conjunto de workers como uma lista rígida de dependências obrigatórias. Indisponibilidade de um único worker, inclusive por dependência intermediária como ProxyJump, é promovida incorretamente a indisponibilidade total do serviço de CI distribuído.

### Solução estrutural já desenhada

A PR #183 — `feat: add capability-based distributed CI host registry` — introduz:

- registry local de hosts;
- seleção por capability `postgres-worker`;
- dependências explícitas;
- health reconciliado;
- pool degradável;
- requeue quando infraestrutura desaparece;
- distinção entre falha de infraestrutura e falha real de teste;
- failover do reprofile.

A PR #183 provou o conceito com um gate real de 444 testes em três workers. Porém sua branch ficou desatualizada em relação à `main` e não deve ser mergeada cegamente.

### Impacto

- bloqueia PRs sem relação causal com o CI;
- impede merge protegido mesmo com workers suficientes disponíveis;
- transforma manutenção/offline de um host auxiliar em pane global do gate;
- bloqueou diretamente a certificação OpenTelemetry do Worker.

### Correção mínima proposta

Reaplicar a arquitetura V2 da PR #183 sobre a `main` atual, executar os checks atuais e fazer bootstrap controlado do control plane com rollback para o scheduler V1.

O bootstrap não deve marcar o gate como verde artificialmente. O objetivo é permitir que o gate real rode nos workers atualmente saudáveis e publique seu resultado normal.

### Observabilidade obrigatória

O check deve publicar:

- scheduler version;
- configured pool;
- ready pool;
- host dependency state;
- degraded=true/false;
- workers efetivamente utilizados;
- requeued file count;
- classificação `TEST_FAILURE` vs `WORKER_LOST`/infra;
- wall time e total de testes.

### Teste de regressão

Cenário obrigatório:

1. três workers configurados;
2. dependência de um worker indisponível;
3. dois workers READY;
4. gate continua em modo degradado;
5. todos os arquivos são redistribuídos;
6. suíte real passa;
7. resultado final é PASS + `degraded=true`.

Também provar que uma falha real de pytest continua terminal e não é convertida em failover.

### Critério de fechamento

- scheduler V2 versionado na `main`;
- control plane efetivamente usando V2;
- PR real validada com `ci03` indisponível e `ci01/ci02` processando toda a suíte;
- rollback documentado;
- AFO-011 citada na evidência da PR que a resolveu.
